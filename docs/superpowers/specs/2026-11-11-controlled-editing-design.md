## Approaches

1. **Recommended: structured edits with application-owned execution.** Models return bounded file proposals and reports. Interspace validates and materializes them, runs a fixed Python test recipe under OS restrictions, and applies a reviewed diff only after approval. Fits the existing text-only provider connection and keeps tool authority outside model output. Initial support is narrower than a general coding agent.
2. **General agent command tools in an isolated checkout.** More flexible for dependencies, builds and languages, but adds command selection, installation, wider reads and process management. An isolated checkout alone does not restrict access to personal files or the network. This is unnecessary for Snack Picker and is deferred.
3. **Export a patch without application.** Smallest write surface, but leaves the requested end-to-end project change unfinished. A reviewable patch can remain an artifact; the recommended version also supports guarded application.

Approval of this document selects approach 1. This is one implementation project, not a new service or framework.

## User flow and approvals

1. **Plan.** The Orchestrator receives the selected committed context and proposes assignments, disjoint write paths, code-versus-test path classification, the fixed test recipe and exact model-call ceiling. Existing changed paths must be approved selected sources. New paths must be listed explicitly before Start; they cannot overwrite unselected or untracked files. At least one code path and one test path are required. Test paths are Python files below `tests/`; code paths cannot be below `tests/`. Scope and source revision/selection version are bound into the plan digest.
2. **Start proposal generation.** Approval binds the complete plan, owner, source scope and limits. Researchers and Implementers run; Interspace validates each structured replacement and writes it only into the candidate copy. Models receive no file-writing or command tools. Source content and model output are untrusted data. The original checkout remains unchanged.
3. **Inspect candidate.** Activity stops at `awaiting_test_approval`, with a visible diff, new files, candidate digest, exact test recipe, expected red/green outcome and remaining model calls. No generated code has executed yet. Stop/abandon preserves artifacts. A source change, candidate change or replacement plan invalidates this approval opportunity.
4. **Run checks & finish review.** A separate action binds the exact frozen candidate, proposed test files and recipe. Interspace durably reserves at most three deterministic test processes, captures their actual results, then dispatches Tester analysis, Reviewer jobs and synthesis within the original model ceiling. No extra calls, commands, retries or repair loop are inferred from a failed check or Reviewer objection.
5. **Inspect result.** Result shows the patch, original-suite outcome, regression-against-original outcome, candidate-suite outcome, actual exit codes/output, review verdicts, citations and unresolved questions. A process success is not presented as proof of semantic correctness. Ready-to-apply requires the supported red/green test conditions, unanimous Reviewer acceptance, successful synthesis, unchanged candidate and source integrity.
6. **Apply reviewed changes.** A distinct final action binds project/task/run, plan digest, candidate/test-result/report identity and the exact diff. This writes only those files to the original project, leaves them uncommitted and records the application outcome. It is separate from report acceptance. A duplicate or stale action cannot write again. After application, the UI explains that future committed-source plans need a new source commit/selection; Interspace does not create that commit automatically.

The test-approval pause is durable and releases the global active interaction slot. Resuming is an explicit action, not an automatic retry. The UI may navigate between tasks/projects while paused without changing any owner or approval reference.

## Fixed Python check recipe

The first recipe is standard-library `unittest` discovery under `tests/`, with no extra arguments supplied by a model. Interspace uses the Apple Python 3 runtime, resolves its actual executable once and binds that runtime identity and recipe version into execution approval. Unsupported or unavailable runtimes make execution unavailable; there is no unrestricted fallback.

After exact candidate approval, run at most these three processes, each once:

1. Original committed code with original committed tests.
2. Original committed code with the candidate's approved test files overlaid; this is the discriminating regression check.
3. Candidate code with exactly those same candidate tests.

For this bug-fix preset, original tests must pass with at least one discovered test; the regression check must fail with at least one assertion failure and no discovery/import/runtime errors; candidate tests must pass with at least one discovered test. Timeouts, cancellations, missing results, output limits, errors and no failing regression are recorded distinctly and prevent ready-to-apply. A correct change without a discriminating regression can still be inspected; it is not automatically integrated. Future feature/build recipes require separate design.

The application, rather than a model, owns executable selection, arguments, environment, working directories, timeouts and reservation counts. Tester is a real model assignment analyzing actual captured results, not a label for invented test activity. Repeated Testers analyze the same immutable check bundle; they do not implicitly multiply process reservations.

## Test execution boundary

Use the installed macOS process-restriction facility through the fixed system launcher. The test profile starts with operations denied and grants only reads of the materialized check tree and required Apple Python/system runtime files, writes to a fresh per-process scratch directory, necessary runtime metadata/container queries and self-signalling. It must not grant access through the broad `/System` tree, which includes the Data volume. No general service-lookup permission, source-project access, application-state access, network permission or child-program permission is granted. Python runs with isolated mode, site initialization disabled and bytecode writing disabled; the trusted harness adds only the check tree needed for discovery. Candidate and baseline trees stay read-only during checks.

Use a minimal fresh environment with application-owned HOME/TMPDIR, no inherited provider/cloud credentials or Python configuration, no stdin, a new owned process group, a 30-second wall deadline, bounded CPU/file-size/open-file/process resources and a 100,000-byte combined output ceiling per check. Capture exit/signal, duration, truncated/limit status and stdout/stderr. Stop and deadlines terminate the owned process group, including after its leader exits. Failure to establish restrictions is a failed/unavailable check, never permission to run without them. No test is launched by merely previewing a task or opening an artifact.

The test process executes project code and is not assumed trustworthy. OS restrictions provide the access boundary; passing output and test assertions still require code review. Tests running in one Python interpreter are not a proof against deliberately fraudulent assertions or test-framework monkey-patching. Do not describe this milestone as general hostile-code containment or model accuracy certification.

## Guarded application and recovery

Before application, revalidate all approval identities, plan/source scope, HEAD, original tracked-file baseline, candidate/diff/check/report hashes and Reviewer verdicts. Existing target bytes must match their approved original blob; new targets must still be absent. Reject symlinked roots/parents/targets, path aliases and targets with unexpected type/link metadata. Use descriptor-relative, no-follow file operations for source writes; never execute the source repository or its configuration/hooks as part of applying a change. Any Git reads used for this path disable optional locks, hooks and filesystem-monitor helpers.

Write a durable application journal and original backups before the first source replacement. Stage complete new file contents and preserve supported original file permissions. A byte check followed by an ordinary replacement is insufficient: preserve the exact displaced source entry as part of the atomic operation, then verify its content against the expected original. Use a supported atomic exchange primitive for existing files and exclusive creation for new files, with descriptor-relative paths. Retain the displaced entry and competing bytes for recovery. For this first version, applying is available only when source and application staging storage share a filesystem that supports those primitives; otherwise retain the tested patch and explain why application is unavailable. Never fall back to a destructive check-then-replace or cross-filesystem copy.

Multi-file application is not one atomic filesystem transaction: if an in-process failure occurs, roll back only files still owned by this operation, preserving any competing bytes displaced by rollback as well. If an external edit prevents safe rollback, preserve it and mark `recovery_required`. Test a competing edit between validation and exchange explicitly; detected conflicts must not be recorded as `applied`. This does not assert that arbitrary external editors can be excluded indefinitely; retained displaced entries preserve the competing content rather than discarding it. On restart, an incomplete journal is surfaced for inspection; it never silently resumes or rewrites the project. Retain backups and a clear list of applied/unapplied files. Do not overwrite user edits in an attempt to hide a partial operation. New directories may be removed during rollback only when created by this operation and still empty.

Application consumes its exact approval. Applying an accepted historical report to a different task, newer candidate or changed checkout fails. Applying a change intentionally changes source integrity; the final state is `applied` with the recorded exact writes, not an unexplained integrity failure. Other pending plans for that project are invalidated. Existing report history remains inspectable.
