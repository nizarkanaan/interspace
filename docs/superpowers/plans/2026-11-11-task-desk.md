# Task Desk Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Deliver the accepted task desk, isolated task conversations/history and multiple specialists per role with user-adjustable team allowances.

**Architecture:** Keep the AppKit/WKWebView shell, Python pipe service and local JSON state. Add a task ownership module; retain old project-level APIs/history for compatibility while new UI work carries explicit task references. Version the repeated-specialist plan policy separately from existing source snapshot formats.

**Tech stack:** Python 3.9+, vanilla JavaScript/CSS, AppKit/WebKit, existing controlled-provider and browser tests.

**Spec:** `docs/superpowers/specs/2026-11-11-task-desk-design.md`, including the accepted editable-allowance amendment.

## Global constraints

- Work on `interspace/task-desk`; preserve unrelated work. No Sample Project access, edits, execution, web research or real provider call for this implementation.
- No new HTTP service, framework, remote fonts, account changes, runtime `.app` test copies or third-party dependencies.
- Team chosen before Start, exact plan digest and source selection approval, one active interaction globally, sequential dispatch, four-minute stage deadline, no retries or recursive spawning.
- Positive JavaScript-safe integer specialist allowance (`1..9007199254740991`), initially `6`, editable per task. No fixed six-agent product cap. Calls after Start are exactly specialist count plus one synthesis.
- Distinguish user task identity from specialist assignment identity; preserve old plan/run/artifact acceptance and migration backups. Source selection changes invalidate all affected unstarted task proposals.
- Use meaningful failing tests before behavioral changes. Controlled providers/disposable repositories only. Coordinator owns Git commits to avoid shared-index races.
- Reuse this approved feature checkout; do not create another worktree. Implement tasks sequentially, with a fresh scoped reviewer after each and a final whole-branch review.

## Review focus

1. Old pending legacy revisions must share their referenced run's imported task, preserve exact approval references and remain usable after restart (Task 2).

5. Late UI replies and unsent drafts must retain task/project identity; switching context must not leak another task's sources or run selection (Tasks 2–3).

## Task 2: Durable task ownership, migration and service APIs

**Files:** create `app/backend/tasks.py`, `tests/test_tasks.py`, `tests/test_task_workflow.py`; modify `app/backend/projects.py`, `app/backend/service.py`, `app/macos/main.swift`, existing tests only where legitimate compatibility contracts change. Do not edit team/policy/UI implementation except report interface concerns to coordinator.

**Consumes:** Task 1 APIs (`validate_specialist_limit`, `chat_schema`, `make_plan` optional arguments, `team.execute(...,task=None)`).

**Produces native bridge APIs:**
- `create_task({project_id,title?,specialist_limit?,draft?})`: local draft; selects it; default title New task and allowance 6. Optional full draft is at most6000 characters and survives reopening. No source/model call.
- `select_task({project_id,task_id})`: restores that task; browsing allowed during active work.
- `update_task({project_id,task_id,title?,specialist_limit?})`: validates selected task; limit changes invalidate its proposal; mutation blocked during work.
- `chat({scope:'task',project_id,task_id,text})`: task-only history and same task's selected prior run. Existing workspace/project general conversations remain separately available. New task plans use policy 2 and bind task ID.
- Existing task-scoped `start_plan`, legacy `start_review`, `source`, `select_run`, `revise_run`, `accept_report` carry `task_id` and independently enforce selected task/project/run ownership. Global cancellation continues to target the actual active interaction.
- Add bridge allowlist entries without widening arbitrary methods or file access.

**Public state contract for Task 3:**
- `tasks`: selected-project task summaries `{id,title,status,specialist_limit,run_count,has_pending_plan}`; optional task metadata may be added compatibly.
- `task_id`: selected task ID or null; `task`: selected `{id,title,specialist_limit,draft}` metadata or null. Old tasks missing draft read as empty without raw rewriting. Task chat consumes it only after consent and durable message storage.
- `threads.task`: selected task conversation; `threads.project` remains the preserved general project conversation. Workspace thread unchanged.
- Top-level `pending`, `run`, `runs` project the selected task when selected; otherwise retain old project-level projection. Task summary status reflects draft/plan ready/actual terminal or active state, never fabricated progress.
- `active_task_id` and `error_task_id` distinguish owner from selection; active owner name visible. Public `error` only applies to the owning context. Source selection stays project-owned.

**State and compatibility:** Add backed-up versioned migration (version 3) after existing v1→v2 migration. Keep originals once. Existing project conversation stays general. Import old runs into tasks without inventing historical chat, preserving run/artifact IDs and acceptance. Pending legacy revision maps to its referenced run's task; old pending proposal is imported unchanged. Never duplicate executable pending approvals in two ownership containers. Keep general old APIs functional for previously authorized legacy flows, but reject missing/mismatched task refs once operating on a selected task. Do not store aliases that can drift between project and task owners. Active recovery must retain owner and terminal results. Re-registration is idempotent. Loading malformed tasks must not overwrite data or break unrelated projects.
